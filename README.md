# Seatwise

校园座位供需治理平台。"系统分析与设计"课程项目，3 人开发。

## 定位

校园预约系统已经商品化，选座、签到、超时释放不构成差异；场馆方仍缺量化依据：放多少座、放多久、高峰何时收紧、一条新规上线后究竟变好还是变坏。Seatwise 因此定位为座位供需的决策层，预约只是必要的底座（SRS 2.1）。

三类能力（SRS 3.6）：

- **底座**：预约状态机（6 状态、6 类结算原因）、签到、暂离与释放、超时回收、只追加的信用账本与申诉。
- **预测**：占用与找座概率（分档 + 校准 + coverage）、期望浪费。
- **治理**：错峰引导、有上限的超额准入、候补补位、峰值轮换、信用优先，以及政策版本化与效果模拟。

数据侧：需求侧用 HKUST 图书馆 WiFi 使用统计（2014-02 至 2022-05，CC0），占用侧用 KTH 图书馆区域占用（2024-12 至 2025-07，仅课程内方法验证，不随仓库分发）。缺预约与签到记录，爽约率与停留时长用假设区间，可迁移比例 θ 是唯一未标定参数。

## 架构（DESIGN 2、3）

模块化单体：api 内按业务能力分 booking / credit / policy / insight / prediction 五个模块，加 identity 与 audit；worker 跑超时释放、指标聚合与漂移检测；ml 离线训练并导出 ONNX 工件，api 用 ONNX Runtime 打分。

四条硬约束：

- 预测只读业务库、只写 `occupancy_prediction` / `waste_estimate` / `simulation_report` 三张结果表，由数据库账号隔离。
- 并发正确性落在数据库：唯一索引 + 行锁 + 状态断言；四类写操作的幂等键是 `(业务键, op, version)`。
- 外部依赖经 4 个端口（占用信号、校历、预测、身份）与 1 个事件出口接入；`policy_version`、`model_version`、`feature_flag` 三个开关让任一能力单独降级，核心流程不依赖预测与 LLM。
- LLM 只保留可选的 L1（一句话 → 检索参数），默认关闭，只回填表单。

## 非目标（SRS 4.1）

对话式助手、政策文本抽取、申诉草拟、运营问答；摄像头与传感器；对接真实校方系统；多校区、支付、原生 App；模型或 LLM 自动执行有副作用的动作。

## 目标指标（SRS 7.x、R8）

| 维度 | 指标 |
|---|---|
| 并发 | 100 并发抢同区域最后 1 座，重复分配 0；四类写操作重放 100 次结果一致 |
| 性能 | 常规接口 p95 ≤ 300 ms、p99 ≤ 800 ms；预测查询 p95 ≤ 150 ms；≥ 20 req/s |
| 预测 | 日粒度需求相对 persistence ≥ 20%；30 分钟前瞻不劣于 persistence 10%；分档校准偏差 ≤ 5 pp；coverage ≥ 90% |
| 可用性 | 表单预约 ≤ 3 步、签到 ≤ 2 次点击；WCAG 2.1 AA；375 px |
| 治理 | 有效利用率 +5%（中性档，区间 +1.8%～+11.0%）、浪费座·分钟 −30%、找座失败率 −25% |
| 成本 | 预测单机 CPU、无外部调用费；L1 单次 ≤ ¥0.01，超月预算自动关闭 |

## 里程碑（SRS 4.2）

| 阶段 | 内容 | 退出准则 |
|---|---|---|
| M1 | 预约引擎：状态机、事务 + 行锁、幂等释放、签到 | 100 并发 0 超卖；释放重复 100 次一致；预约 3 步内完成 |
| M2 | 信用治理、管理后台、报表、申诉 | 5 条计分规则可配；3 张报表可导出；申诉闭环且留痕 |
| M3 | 数据接入与清洗、B1–B3、找座概率与建议、回测与校准 | 日粒度 +20%；30 分钟不劣 10%；校准 ≤ 5 pp；coverage ≥ 90% |
| M4 | 期望浪费、超额准入、政策模拟与归因、开关与回退 | 宽限期 15→20 分钟模拟报告；配额一键关闭；回退不丢数据 |
| M5 | 指标全量测量、降级、演示 | 7.7 每项有结果；关模型与 LLM 下主流程可完成 |

## 仓库结构

```
seatwise/
├── backend/   Spring Boot 4 / Java 25 模块化单体（Maven Wrapper）
├── frontend/  React 19 + TypeScript 6 + Vite 8（pnpm）
├── ml/        离线训练与数据脚本（Python 3.14，uv），不进运行时
└── docs/      需求基线、设计正文、实测证据与图源
```

## 技术栈

- 前端：React 19 + TypeScript 6 + Vite 8，pnpm，lint 用 oxlint
- 后端：Java 25 + Spring Boot 4.1.1，Maven Wrapper，MySQL 8（业务写账号与预测只读账号）
- ML：Python 3.14（uv），离线训练；在线打分用 ONNX Runtime for Java
- 接口：OpenAPI + Apifox，契约先行
- 部署：Docker Compose，web + api + worker + MySQL 四个运行时容器与工件卷
- 可选：LLM API，仅 L1，默认关闭

## 风险与对策（DESIGN 2.5）

| 风险 | 缓解 |
|---|---|
| WiFi 人数 ≠ 座位占用 | 只做需求侧口径，界面标"代理口径"，不参与占用率 |
| θ 未标定 | 三档情景只给区间；G4 闸门未通过不放超额准入 |
| 需求结构漂移（2020 年降至常态 1/5） | 滚动 MAE、份额位移、端口失联三条触发重训与回滚 |
| 预测账号误写业务表 | 数据库权限 + "预测账号写业务表应全部被拒"的验收用例 |
| 单体耦合 | 模块之间只经应用服务接口调用，不跨模块读表 |
| 数据非本校 | 以自建日志复核，外推结论标注来源 |
